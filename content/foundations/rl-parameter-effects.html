RL Parameter Effects¶

Use this reference to interpret run summaries, evaluations and traces. Change one meaningful factor at a time, then compare with fixed evaluation across seeds.

The Four Control Surfaces¶

Most RL results are shaped by four interacting surfaces:

Surface

Examples

What it changes

environment

observation channels, action space, reward, horizon, ProcGen

the actual learning problem

policy/model

MLP/CNN choice, feature extractor, network size, activation

what behavior can be represented

algorithm

learning rate, rollout length, batch size, entropy, discount, target updates

how experience changes the policy

budget/evaluation

timesteps, seeds, eval episodes, env count, walltime

how much evidence the run provides

If two runs differ on several of these at once, the comparison is hard to interpret.

Environment Effects¶

Environment settings can dominate algorithm settings.

Change

Typical effect

observation channels

can make the task solvable, partially observable, or much noisier

observation normalization

can stabilize learning when channel scales differ

frame stacking

adds temporal context but increases input size

action space size

larger discrete spaces and continuous spaces usually need more exploration and budget

reward scale

changes gradient scale and value targets; especially important for PPO and value methods

reward shaping

can speed learning or reward shortcuts

horizon / max steps

changes credit assignment and maximum return

ProcGen distribution

changes whether evidence is about one scenario or a family of scenarios

Do not treat environment wrappers as harmless technical details. If a wrapper changes observations, rewards, termination, or info fields, it is part of the experiment.

Policy And Representation Effects¶

The policy architecture should match the observation.

Observation type

Usual policy choice

small vector

MLP policy

image or spatial grid

CNN or custom feature extractor

channel-first process fields

CNN-style extractor or carefully flattened MLP baseline

mixed vector/grid observations

custom extractor or explicit preprocessing

Common interpretation rules:

  • if a vector task fails, first suspect optimization, reward, horizon, or budget before model capacity

  • if a pixel/grid task fails, representation and preprocessing are often first-order causes

  • if a larger network helps only one seed, repeat before trusting it

  • if a larger network is slower and no better, prefer the smaller baseline

PPO Parameters¶

PPO is sensitive to the relation between rollout collection, update size, and reward scale.

Parameter

If too low

If too high

learning_rate

slow or no improvement

unstable updates or collapse

n_steps

noisy advantage estimates, frequent updates

stale data, slower feedback, larger memory

batch_size

noisy gradient updates

fewer update batches, possible underuse of rollout data

n_epochs

underuses collected data

overfits each rollout batch or destabilizes policy

gamma

short-sighted behavior

high variance for long horizons

gae_lambda

biased advantages

higher variance advantages

clip_range

policy changes too cautiously

large destructive updates

ent_coef

premature deterministic behavior

too much random behavior

vf_coef

weak value learning

value loss dominates policy learning

max_grad_norm

may limit useful updates

weak protection against gradient spikes

When PPO is unstable, first check reward scale, normalization, learning rate, rollout length, and whether the policy matches the observation type.

DQN Parameters¶

DQN is most relevant for discrete action spaces.

Parameter

Main effect

learning_rate

controls value update size

buffer_size

controls replay diversity and memory

learning_starts

delays learning until replay has enough data

train_freq

controls how often updates happen

gradient_steps

controls update intensity per collection step

target_update_interval

stabilizes bootstrapped value targets

exploration_fraction

controls how long epsilon decays

exploration_final_eps

controls final random-action rate

gamma

controls long-term credit assignment

When DQN is weak, inspect exploration first. A low final epsilon or short exploration fraction can make the agent miss useful actions, especially in sparse or long-horizon tasks.

Vectorization And Budget Effects¶

envs, timesteps, and walltime are not just infrastructure settings.

  • more envs can improve throughput but changes the batch of experience seen per update

  • short smoke runs are good for detecting broken setups, not proving final quality

  • long runs without intermediate evaluation can waste budget on a bad configuration

  • fixed evaluation episodes are needed when training metrics are noisy

  • seed count matters more than a tiny reward gap on one run

A useful default research pattern is:

  1. one baseline

  2. one small challenger

  3. fixed evaluation for the better candidate

  4. repeat with another seed

  5. only then widen the search

Reading Learning Curves¶

Use the curve shape, not only the final number.

Pattern

Possible meaning

flat near zero

no useful exploration, bad reward, wrong observation, or too little budget

fast rise then collapse

updates too aggressive, reward scale issue, or policy instability

high variance across episodes

environment stochasticity, sparse rewards, or unstable policy

train improves but eval does not

overfitting to scenarios, train/eval mismatch, or lucky checkpoint

longer episodes but lower reward

reward and survival/length are measuring different behavior

Always check whether the metric is a training monitor, a fixed evaluation result, or a task-specific score.

Next-Run Decision Rules¶

Use these rules before changing a run:

  • if the run failed before training started, debug setup, not hyperparameters

  • if reward is flat, inspect environment/reward/observation before broad tuning

  • if one challenger wins on one seed, repeat the seed before making a claim

  • if behavior is unclear, request eval or trace analysis instead of adding many runs

  • if several parameters changed, do not overinterpret the result

  • if the task is physical or process-oriented, inspect diagnostics such as success, physics, temperature, coverage, invalid actions, and runtime failures

What Counts As Evidence¶

Good evidence usually includes:

  • the exact environment/task/algo/variant

  • the changed parameter or run config

  • seed count

  • budget and env count

  • training metric

  • fixed evaluation metric when available

  • relevant environment diagnostics

  • whether there are counterexamples

Study-local notes may contain hypotheses. Reusable lessons should be manual and conservative.
