Grid-Style RL Experiments¶

This page collects practical research lessons from 2D grid-style reinforcement learning environments and maps them to CTRL-P tasks such as FFFLite, PBFLite, and DAWN fill-style environments.

The goal is not to copy another benchmark. The goal is to understand which experimental controls matter when an agent moves over a 2D surface, chooses local actions, and receives reward from coverage, navigation, collection, or process quality.

Why Grid Environments Are Useful¶

Grid environments are useful because they separate parts of the RL problem.

They can be made:

  • small enough for rapid debugging

  • discrete enough for tabular or DQN baselines

  • spatial enough to test CNN policies

  • partially observable enough to test memory and state inference

  • procedurally generated enough to test generalization

  • sparse enough to test exploration and curriculum design

This is why grid-style environments appear in many RL benchmarks, from simple Gymnasium toy-text environments to FFFLite, Procgen, MinAtar, BabyAI, and MiniHack.

Benchmark family

What it studies

Why it matters for CTRL-P

Common Structure¶

Most grid-style RL environments share these ingredients:

Component

Typical form

Experimental risk

state

grid cells, agent location, objects, process fields

full state may be much richer than observation

observation

cell id, local view, image, or channel tensor

partial observability can look like weak learning

action

move directions, toggle/use/pickup/drop, process controls

larger action sets increase exploration cost

transition

deterministic, stochastic, or physics/process update

stochasticity can hide whether a change helped

reward

goal reward, step cost, coverage, penalties

shaping can reward shortcuts

termination

goal, failure, timeout, invalid transition

horizon changes alter difficulty and maximum return

scenario generation

fixed map, random map, train/test split

narrow scenario sets can cause overfitting

CTRL-P FFFLite, PBFLite, and DAWN share the same high-level shape, but the transition model becomes progressively more process-oriented.

Observation Lessons¶

Grid environments can expose the task in several ways.

Observation type

Example

Implication

discrete state id

toy-text grid worlds

tabular methods are meaningful baselines

full grid tensor

MinAtar, many custom grid worlds

CNNs or small spatial encoders can exploit locality

egocentric local view

FFFLite

memory may be needed because the full state is hidden

RGB image

Procgen, Atari-like tasks

representation learning becomes a major part of the result

channel-first process fields

CTRL-P FFFLite/PBFLite/DAWN

each channel should be treated as a meaningful physical or task signal

For CTRL-P, this means:

  • if the observation is phase/load/mask/temp, the channel set is part of the experiment

  • adding temperature can change the problem from geometric coverage to thermal control

  • a CNN-style feature extractor is often more natural than a plain MLP for grid tensors

  • if the agent only sees a local or modified view, poor behavior may be partial observability rather than bad optimization

Action-Space Lessons¶

Small grid tasks often look easy until the action set changes.

Action design

Effect

4-neighbor movement

simple navigation and coverage

8-neighbor movement

shorter paths but larger branching factor

toggle/use actions

introduces timing and mode decisions

pickup/drop/open actions

introduces object and state dependencies

layer up/down actions

adds a hidden dimension to what looks like a 2D grid

continuous movement/process controls

shifts problem toward continuous-control methods

invalid actions

can waste exploration unless masked or penalized carefully

For CTRL-P:

  • FFFLite and PBFLite movement actions should be interpreted together with TOGGLE

  • DAWN multilayer actions are not just more buttons; they change the planning structure

  • invalid-action counts are evidence about action-space design, not only policy quality

  • when action count changes, do not compare learning curves as if the task stayed identical

Reward Lessons¶

Grid-style rewards often mix several objectives.

Reward pattern

Common issue

sparse goal reward

exploration is hard; flat curves are common

dense distance reward

may reward moving closer without solving

coverage reward

can reward redundant or imprecise coverage

step penalty

encourages efficiency but can punish necessary exploration

failure penalty

can dominate learning if too large

shaped intermediate rewards

faster learning, but possible shortcuts

For CTRL-P fill-style tasks, reward is usually not just “fill more.” It often balances:

  • target coverage

  • precision inside the mask

  • redundant processing

  • completion

  • step cost

  • physical/process diagnostics

This means a higher return is not automatically a better process. Inspect score, success, coverage, redundant fill, temperature, invalid actions, runtime failures, and traces when available.

Procedural Generation And Generalization¶

Procgen and FFFLite-style task generation show a recurring lesson: agents can overfit to narrow scenario sets even when the environment appears varied.

Useful controls:

  • fixed seed smoke test for debugging

  • multiple train seeds for learning stability

  • held-out validation or test scenarios for generalization

  • scenario identifiers in logs

  • explicit distinction between “solved this layout” and “learned this task family”

For CTRL-P:

  • a fixed mask/load task is a debugging surface

  • a generated mask/load distribution is a generalization surface

  • train, validation, and test ProcGen splits should not be mixed in claims

  • evidence from fill and thermo_medium or depo_medium should be scoped separately unless both support the same conclusion

Curriculum Lessons¶

Grid benchmarks often use a difficulty ladder.

Examples:

  • small map before large map

  • deterministic dynamics before stochastic dynamics

  • full observation before partial observation

  • sparse task after dense diagnostic task

  • single-room navigation before multi-room navigation

  • one layer before multilayer control

For CTRL-P, a sensible ladder is:

  1. CartPole or another cheap runtime smoke test

  2. CTRL-P FFFLite fixed/simple fill

  3. FFFLite larger or generated fill

  4. PBFLite fixed/simple fill

  5. PBFLite larger/generated fill

  6. DAWN dawn/pbf/thermo_small

  7. DAWN multilayer or larger tasks

Do not jump to DAWN when the same failure can be diagnosed in FFFLite or PBFLite.

Algorithm Lessons For Grid Tasks¶

Situation

Good first algorithm choices

Notes

tiny discrete state

tabular Q-learning or SARSA

useful sanity check if state is explicit

discrete full-grid tensor

DQN or PPO with CNN features

compare value-based and policy-gradient behavior

sparse reward navigation

DQN/PPO plus exploration or curriculum

expect flat curves without enough exploration

partial observability

recurrent policy, frame stacking, or belief features

MLP may fail even when task is solvable

channel grid with process fields

PPO/DQN with task-specific feature extractor

channel scaling and normalization matter

continuous process controls

PPO/SAC/TD3 style methods

action scaling and reward scale are critical

For quick CTRL-P studies, PPO is often convenient because it handles many observation/action surfaces. DQN is useful when the action space is discrete and the question is about value learning or exploration. Behavior cloning is useful when a heuristic can generate meaningful demonstrations.

Evaluation Lessons¶

A grid RL result should usually report more than one scalar.

Useful metrics:

  • return or task reward

  • episode length

  • success rate

  • score or task-specific quality metric

  • invalid-action count

  • scenario id or ProcGen split

  • action histogram

  • coverage/precision/redundancy

  • physical/process diagnostics when available

  • seed mean and spread

For small studies, a good minimum is:

  1. training curve

  2. fixed-evaluation mean and spread

  3. at least two seeds before making a study-level claim

  4. one trace or demo when behavior matters

Failure Triage¶

Use this order before changing hyperparameters:

  1. Did the run fail before training? If yes, debug setup.

  2. Does check pass? If no, debug config/environment/model construction.

  3. Is reward flat but actions vary? Inspect reward and horizon.

  4. Is reward flat and actions collapse? Inspect exploration, entropy/epsilon, and action scaling.

  5. Does training improve but eval fail? Inspect train/test scenarios and overfitting.

  6. Does reward improve but process diagnostics worsen? Inspect reward shaping.

  7. Does one seed win? Repeat before broadening the search.

What To Put In notes.md¶

For each meaningful step, write:

  • what changed

  • what evidence was observed

  • what explanation is most likely

  • what explanation is still uncertain

  • what smallest next run reduces that uncertainty

Example:

## Current Interpretation

The PPO challenger improves reward on seed 0, but this is only one CartPole-style smoke result.
The next useful step is a fixed evaluation and one repeated seed, not a broad sweep.

Practical Rule For Autoresearch¶

For grid-style CTRL-P studies, the agent should usually choose the next step in this order:

  1. verify the current setup with resolve/check/short train

  2. compare one small challenger against one baseline

  3. request fixed evaluation if one looks better

  4. repeat the better setting with another seed

  5. inspect trace/demo if reward and behavior disagree

  6. only then widen to HPO or larger task variants

The goal is to reduce uncertainty, not to launch many runs.
