Config¶

CTRL-P uses one canonical run-config layout. <env...> may contain multiple path parts, for example dawn/pbf or lite/fff.

experiments/<env...>/runs/<task>/<algo>/<run>/run.yml

The path selects the task, algorithm and run; run.yml supplies the manifest and runtime settings. parameters.yml in the same folder is a generated snapshot, not an editable source file.

eval, demo and rollout prefer the snapshot when available. resolve, check, train, pretrain and hpo use editable sources. Demo defaults to live playback and falls back to scripted playback without a display. HPO reads its search space from experiments/<env...>/presets/hpo/<algo>.yml.

For the exact per-mode inputs, use Mode Inputs. For the Python modules behind config resolution, use Runtime API.

Run Config Schema¶

select:
  env: dawn/pbf
  task: layer
  algo: ppo
  run: default

presets:
  procgen: single
  reward: default
  vec: default

runtime:
  # Omit this block to retain the Stable Baselines3 default.
  trainer:
    engine: sb3
    topology: single_node

  sweep:
    seed: [0]

  train:
    timesteps: 1.e5
    eval:
      frequency: 10
      episodes: 10

  eval:
    episodes: 20
    checkpoint: best_model.zip

  inference:
    type: sweep
    checkpoint: best_model.zip
    seeds: all

Naming Rules¶

  • run configs live under experiments/<env...>/runs/

  • <task>/<algo>/<run>/run.yml is the canonical run-config path

  • the YAML file must contain both select and runtime

  • select.env, select.task, select.algo, and select.run must match the path

  • presets.procgen selects the procgen preset or dataset variant for the task

  • presets.reward and presets.vec select short preset names; both default to default when omitted by generated inputs

  • presets.algo_preset optionally selects presets/algo/<algo>/<name>.yml

  • select validates the manifest; the path is the user-facing entrypoint on disk

  • HPO settings live inside runtime.hpo in the default run config for that task

  • HPO search spaces live in presets/hpo/<algo>.yml

Note

task here is the experiment selector. The runtime operation is called mode and is passed at the CLI with --mode.

Parameter Tree¶

The run config resolves against the env-local parameter tree:

experiments/<env...>/
  presets/
    tasks/
      <task>.yml
    procgen/
      default.yml
      <name>.yml
    hpo/
      ppo.yml
      bc.yml
      dqn.yml
    algo/
      ppo/
        base.yml
        smoke.yml
        tasks/
          <task>.yml
      dqn/
        base.yml
    assets/
      <task>/
  studies/
    <study-id>/
      manifest.yml
  runs/
    <task>/
      <algo>/
        <run>/
          run.yml
          parameters.yml
          agents/

Multi-part environment folders are valid. For example, DAWN PBF run configs live under experiments/dawn/pbf/... and use select.env: dawn/pbf.

Meaning¶

Key

Meaning

select

experiment identity: env, task, algo, run

presets

short reusable preset choices: procgen, reward, vec, optional algo_preset

runtime

Trainer Selection¶

Omitting runtime.trainer preserves the established mapping: Torch algorithms use Stable Baselines3, JAX algorithms use SBX, and CTRL-P heuristics use their native implementation. Device vectorization without an explicit engine selects native JAX PPO instead. Explicit selection is fail-closed:

See Trainer compatibility for physics/vector requirements, action masks, supported modes and concrete controls. Framework selection alone does not make an environment device-resident.

TorchRL is an opt-in pilot. It does not accept action masking, recurrent policies, cross-engine resume, or multi-node execution. Only resolve, check, train, eval, and demo are enabled; other modes fail closed until they have backend-parity tests. Every run writes checkpoint-index.json, which identifies its engine, format, files, sizes, and SHA-256 hashes. best_model.zip remains the public legacy selector; trainer-aware loading resolves it to best_model.pt for TorchRL.

See Model lifecycle for verified checkpoint initialization, fine-tuning, trainability schedules, and composition manifests.

TorchRL PPO accepts numeric or lin_... schedules for learning_rate and clip_range, and emits SB3-shaped rollout, optimization, KL, explained variance, FPS, and elapsed-time metrics. Same-engine resume restores policy, optimizer, and Python/NumPy/Torch random-number state and fails closed when the saved spaces, policy shape, or PPO configuration differs. It deliberately resets the environment at a reproducibly seeded episode boundary; simulator state is not checkpointed and continuation is therefore not bit-exact.

run is the concrete run name. It must match the run config name or the run directory name:

  • experiments/dawn/pbf/runs/thermo_small/ppo/default/run.yml -> run default

  • experiments/lite/fff/runs/depo_small/ppo/default/run.yml -> run default

  • experiments/lite/fff/runs/depo_medium/ppo/smoke/run.yml -> run smoke

Merge Order¶

CTRL-P resolves parameters in this order:

  1. package environment defaults from src/ctrlp/environments/<env>/defaults/

  2. presets/tasks/<task>.yml

  3. selected ProcGen preset from presets/procgen/<task>/ or presets/procgen/, if any

  4. selected reward preset from presets/reward/<task>/algos/<algo>/, layered on top of presets/reward/<task>/ when both exist; falls back to presets/reward/<task>/<algo>/ for legacy layouts and presets/reward/ for global defaults

  5. selected vectorization preset from presets/vec/<task>/algos/<algo>/, layered on top of presets/vec/<task>/ when both exist; falls back to presets/vec/<task>/<algo>/ for legacy layouts and presets/vec/ for global defaults

  6. package algorithm defaults from src/ctrlp/learning/algorithms/.../parameters/

  7. presets/algo/<algo>/base.yml

  8. presets/algo/<algo>/tasks/<task>.yml

  9. optional presets/algo/<algo>/<name>.yml selected with presets.algo_preset

  10. presets/hpo/<algo>.yml when the mode is HPO

  11. runtime and overrides from experiments/<env...>/runs/<task>/<algo>/<run>/run.yml

  12. runs/<task>/<algo>/<run>/parameters.yml only when loading a saved snapshot

Task presets own environment/task semantics only. Reward shaping lives in presets/reward/, vectorization and rollout wrapper defaults live in presets/vec/, and algo presets contain only algo and policy blocks. Run overrides are the final editable diff.

Validation Rules¶

  • run configs must match experiments/<env...>/runs/<task>/<algo>/<run>/run.yml

  • the select block must match the path

  • presets accepts only short names: procgen, reward, vec, and optional algo_preset

  • unknown top-level keys are rejected

  • runtime accepts only backend, trainer, sweep, inference, train, eval, rollout, pretrain, hpo, and demo

  • always pass the experiment file path; CTRL-P no longer falls back to a root config.yml

  • pass a run directory directly when you want to run from runs/<task>/<algo>/<run>/run.yml

  • do not edit runs/<task>/<algo>/<run>/parameters.yml; it is regenerated output

Gym Environments¶

For a Gymnasium env such as CartPole-v1, CTRL-P bootstraps missing env-local files on the first executable run:

      default.yml

      ppo.yml
    algo/
