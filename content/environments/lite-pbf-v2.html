PBFLite V2¶

Purpose¶

PBFLite V2 is the maintained lightweight thermal FEM environment. It was built as a separate environment so that historical lite/pbf policies and traces remain reproducible.

Use lite/pbf-v2 for new Lite PBF work. Use legacy lite/pbf only when replaying or comparing an existing study.

PBFLite V2 is a thermal process surrogate. It does not currently model latent heat, fluid flow, plasticity, stress, displacement, or residual distortion.

Mask sizing is versioned. Historical configurations retain the original full-domain area meaning; new boundary-safe configurations can opt into the shape-preserving contract described in Lite PBF V2 mask sizing.

Use the corresponding control with the -source-control run suffix for new learned-power experiments. The optional presets.task selects a complete task YAML; if omitted, the resolver uses select.task as before. Missing explicit task presets fail resolution. Do not change power limits between training and evaluation of the same policy; compare different limits as different physical tasks. This migration does not redefine Easy/Easy+ ProcGen or their power budgets.

Completed runs remain tied to their saved resolved configuration and code provenance. Moving an executable study to the new task changes its source fingerprint even when all resolved physical and training parameters match.

Mathematical Model¶

The solver advances the 2D heat equation with Q4 finite elements:

\[ \left(\frac{C}{\Delta t} + K + H\right)T_{n+1} = \frac{C}{\Delta t}T_n + f_{\mathrm{source}} + f_{\mathrm{boundary}}. \]

  • C is the consistent or lumped thermal-capacity matrix.

  • K is the in-plane conduction matrix multiplied by layer thickness.

  • H contains implicit surface and edge convection.

  • temperature, heat-flux, convection, and adiabatic edge conditions are distinct.

Element matrices are integrated through each element Jacobian. Rectangular cells are supported; square cells are not assumed.

The Gaussian source is integrated analytically against the bilinear shape functions. It is therefore not sampled only at nodes and can remain meaningful when its standard deviation is smaller than a cell. With the default boundary_policy: renormalize, the equivalent nodal load sums to the configured absorbed power.

State Semantics¶

The default observation has six channels:

Channel

Meaning

mask.processed

cells that have ever reached the melt threshold

mask.molten

cells currently at or above the melt threshold

source.0.field

continuous Gaussian source footprint and activation state

source.0.param.power

current absorbed source power, scaled for observation and broadcast spatially

mask.target

target geometry

field.temperature.cell

temperature normalized over the configured observation range

mask.processed records task history, not a physical solid/liquid phase fraction. mask.molten is also only a temperature-threshold field until an enthalpy model is implemented. These are physical-state-v1 selectors; old short-name contracts require explicit conversion and are not accepted as aliases in new controls. The physical export retains SI temperature/power separately from observation scaling; see physical trajectories.

The temperature observation range must include overheat_temperature. This is validated at startup so that the policy cannot accidentally receive identical observations for melting and overheating.

env.obs.grid decouples policy resolution from solver resolution. Uniform cell fields are projected with conservative overlap weights, so constants and domain means are preserved. The 40 x 40 training and 80 x 80 reference meshes can therefore expose the same 20 x 20 policy observation.

Diagnostics¶

Strict defaults compute an energy_balance block in info["physics"] every step:

  • source power;

  • net prescribed-boundary power;

  • temperature-constraint reaction power;

  • stored-energy rate;

  • absolute and relative balance residual;

  • free-equation algebraic residual.

Training presets set model.runtime.diagnostics_interval: 50. The most recent balance remains visible together with energy_balance_age_steps. Changing the interval skips diagnostic work only; it does not change the thermal solution.

The training curriculum starts the source active at 30 W and uses 1 m/s, giving 30 J/m line energy. Its action set includes movement, STAY, TOGGLE, SOURCE_DOWN, and SOURCE_UP. The intensity actions change absorbed power by model.source.power_step and clamp it to power_min/power_max; the defaults provide 7.5 W, 15 W, 22.5 W, and 30 W levels. The current power is included in the observation. Rejected boundary or power actions are reported as invalid_action and receive a small explicit penalty in the plain-PPO curriculum.

Changing from the earlier six-action curriculum to this eight-action surface changes the policy output layer. Train a new policy or use the explicit checkpoint action-adaptation workflow when reusing an older checkpoint.

thermal_progress supplies a dense potential difference as target cells move from the initial temperature toward the melt threshold. thermal_spillover penalizes new off-target progress. Hard threshold melt history still determines coverage and success.

The scale-independent CNN preset uses one frame, [32, 64] convolution channels, and a 20 x 20 maximum feature grid. Ordinary training disables raw rollout-info capture. On the current CPU, subprocess vectorization is the throughput default. vec.type: batch shares one FEM factorization and supports multi-RHS stepping; it is useful when factorization memory dominates, but remains opt-in until it outperforms subprocess execution end to end.

Optional JAX/GPU execution¶

CPU/SciPy remains the default and reference implementation. GPU execution is an explicit three-part opt-in: choose model.runtime.physics_backend: jax, a vec.type: device preset, and runtime.trainer.engine: ctrlp_jax. The device runtime reuses the canonical SciPy-assembled operators, batches solver state and environment transitions in JAX, and independently certifies each linear solve. Requesting vec.device: gpu fails if JAX cannot see a GPU; it never silently falls back to CPU.

The current device trainer is a bounded PPO qualification path on one GPU. JAX policy inference and environment transitions remain on device for each rollout chunk; the established SBX PPO update and checkpoint surface is retained. It is therefore not yet a fully device-native optimizer. Frame stacking, observation/reward normalization, raw rollout-info capture, and observation modifiers fail closed until device-native equivalents exist. Check, evaluation, and demo retain the normal bounded host-vector lifecycle.

ProcGen inputs are materialized into a deterministic scenario bank before JIT execution. Each training attempt saves the bank arrays and a SHA-256 receipt in agent/scenario-bank/. Exhaustion advances by batch stride and records wrap counts. CPU and JAX execution share the environment contract, while backend, precision, solver, device, component code, and scenario-bank hashes remain explicit execution provenance.

Use the tracked thermo_medium/ppo/gpu-smoke control only as an integration gate. Throughput comparison is maintained in private research tooling. A speedup does not establish policy parity: promotion still requires fixed- scenario evaluation and the existing DAWN transfer contract.

For a bounded training-path profile, add algo.profile_device: true to the run override. The trainer records profile/device_scan_seconds, profile/device_to_host_seconds, profile/rollout_buffer_seconds, profile/callback_seconds, profile/gae_seconds, and profile/ppo_update_seconds in the normal progress stream. This option adds explicit synchronization and should remain disabled for ordinary runs. It is intended to answer whether host buffering or PPO updates dominate; it does not change the CPU reference path or rollout semantics.

Rendering¶

PBFLite V2 uses the shared 2D/3D scientific field viewer rather than the legacy Lite grid renderer. The default is a perspective composite of temperature, target outline, melt history, source state, and active/inactive toolpath. The temperature scale is fixed from ambient to the overheat threshold so colors can be compared between steps and mesh resolutions.

The viewer is created only when render() or render_surface() is called, so ordinary training does not initialize Pygame or build render scenes. Available controls are:

The render scene is separate from the policy observation. It supports 2D surface meshes, structured 3D cells, point/cell/volume fields, named vector and tensor components, and optional displacement-based geometry deformation. PBFLite remains a 2D thermal model; these capabilities are an extension surface, not a claim that 3D or mechanical physics is already implemented.

Configuration Safety¶

PBFLite V2 converts YAML into frozen configuration objects before creating the mesh. Unknown keys, missing units-bearing settings, non-positive dimensions, conflicting corner temperatures, unsupported material models, invalid actions, and inconsistent observation limits raise descriptive exceptions.

The package defaults contain comments next to every physical value. Start from those defaults rather than assembling an untyped model dictionary in Python.

Future Thermomechanical Extension¶

Thermomechanics is intentionally not implemented yet. The extension boundary is already present:

  1. ThermalProcessModel.snapshot() returns read-only nodal temperature, cell temperature, current threshold state, and melt history.

  2. PhysicalState records each scalar, vector, or tensor field’s node/cell location, component names, shape, units, data type, and observation scaling.

  3. ThermalMaterialModel isolates thermal constitutive evaluation.

  4. The Gym environment depends on the process model rather than directly on FEM matrices.

  5. PostThermalPhysicsModule provides field-registration, reset, and post-step update hooks for one-way coupled modules without putting mechanics in the environment.

A first mechanics implementation should consume the thermal snapshot and add separately named displacement, strain, and stress fields. It should not put mechanical calculations into env.py or overload the threshold mask.molten field.

The optional model.coupling mapping exposes this seam directly. Its mechanics selector is none (default), zero (nonphysical field/rendering plumbing), or student (the deliberately unfinished research continuation). Its formulation is explicitly plane_stress or plane_strain. Device-vector execution rejects enabled post-thermal mechanics until a device-native module exists; host execution retains the shared state and renderer.

Both Lite V2 environments also accept SI-valued ProcessCommand objects below their Gymnasium action surfaces. The direct demo is available with:

python -m ctrlp.environments.lite.demo --env pbf-v2 --controller keyboard
python -m ctrlp.environments.lite.demo --env pbf-v2 --controller gcode \
  --path examples/lite/pbf-zigzag.gcode

The supported G-code subset is absolute G0/G1 X Y F, G4 P/S, M3/M5, and the M106/M107 on/off aliases. Coordinates are millimetres, feed is millimetres per minute, and M3 S is absorbed PBF power in watts. Segments are interpolated into physical timesteps; SciPy caches the shorter final-step factorization required to reach an endpoint exactly.

Recommended progression:

  1. one-way temperature-to-linear-thermoelastic coupling;

  2. explicit plane-stress or plane-strain selection;

  3. mechanical supports and traction boundaries;

  4. activation and stress-free temperature history;

  5. plasticity only after verification against an independent solution.

Verification Contract¶

The focused numerical tests check:

  • constant-temperature invariance;

  • exact absorbed-power conservation on multiple rectangular meshes;

  • decreasing one-step peak-temperature error under Gaussian-source mesh refinement;

  • a linear manufactured temperature solution;

  • stepwise energy balance;

  • periodic-diagnostic equivalence;

  • conservative fixed-policy-grid projection;

  • batched versus independent thermal steps;

  • generic 2D/3D render-scene validation and PBFLite scene orientation;

  • perspective, top-view, volume-slice, vector/tensor, and deformation rendering;

  • temperature observation semantics;

  • immutable coupling snapshots;

  • Gymnasium reset, step, and invalid-action behavior;

  • independent legacy and V2 registry entries.

Run them with:

PYTHONPATH=src .venv-wsl/bin/python -m pytest -q tests/environments/test_lite_pbf_v2.py

Then validate the shipped experiment surface:

PYTHONPATH=src .venv-wsl/bin/python ctrlp.py \
  experiments/lite/pbf-v2/runs/thermo_small/ppo/smoke/run.yml --mode resolve

PYTHONPATH=src .venv-wsl/bin/python ctrlp.py \
  experiments/lite/pbf-v2/runs/thermo_small/ppo/smoke/run.yml --mode check

PYTHONPATH=src .venv-wsl/bin/python ctrlp.py \
  experiments/lite/pbf-v2/runs/thermo_medium/ppo/train/run.yml --mode check
